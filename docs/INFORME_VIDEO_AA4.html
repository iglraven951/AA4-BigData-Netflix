1. CASO, PROBLEMA, OBJETIVOS Y DATOS

Integrante 1 - Tiempo: 3 minutos

1.1 Presentacion del Caso de Estudio

Netflix es una empresa estadounidense de entretenimiento fundada en 1997 que ha revolucionado la industria del consumo audiovisual. Actualmente opera en mas de 190 paises con mas de 230 millones de suscriptores, generando diariamente petabytes de informacion proveniente de interacciones de usuarios, visualizaciones de contenido, valoraciones, busquedas y patrones de comportamiento.

El modelo de negocio de Netflix se basa en suscripciones mensuales con diferentes niveles (Basico, Estandar, Premium), y su exito depende fundamentalmente de dos pilares: la capacidad de recomendar contenido relevante a cada usuario, y la habilidad de tomar decisiones de produccion de contenido original basadas en datos de consumo. Ambos pilares requieren capacidades avanzadas de analisis de grandes volumenes de datos.

El ecosistema de datos de Netflix incluye:

  • Datos de catalogo: Informacion de mas de 15,000 titulos incluyendo metadatos, generos, elenco y clasificaciones.
  • Datos de usuarios: Perfiles de 230+ millones de suscriptores con preferencias, historial y datos demograficos.
  • Datos de visualizacion: Billones de eventos de reproduccion con informacion de duracion, dispositivo y calidad.
  • Datos de interaccion: Busquedas, navegacion, valoraciones y adiciones a listas.

1.2 Problema Central

El problema central que aborda este proyecto es la incapacidad de los sistemas tradicionales para procesar y analizar eficientemente el volumen, velocidad y variedad de datos generados por una plataforma de streaming a escala global.

Especificamente, los desafios incluyen:

  1. Volumen: Procesamiento de petabytes de datos historicos y terabytes de datos nuevos diariamente.
  2. Velocidad: Necesidad de insights en tiempo cuasi-real para personalizacion y deteccion de anomalias.
  3. Variedad: Datos estructurados (transacciones), semi-estructurados (logs) y no estructurados (thumbnails).
  4. Veracidad: Garantizar calidad y consistencia de datos provenientes de multiples fuentes.
  5. Valor: Transformar datos crudos en metricas accionables para decisiones de negocio.

1.3 Objetivos del Proyecto

Objetivo General: Disenar e implementar una solucion de Big Data que permita el almacenamiento, procesamiento y analisis eficiente de datos de una plataforma de streaming, utilizando tecnologias distribuidas modernas.

Objetivos Especificos:

  1. Implementar lectura de datos desde multiples formatos (CSV, JSON, TXT).
  2. Desarrollar pipeline de limpieza de datos (nulos, duplicados, outliers).
  3. Aplicar transformaciones y crear columnas calculadas.
  4. Integrar multiples fuentes de datos mediante JOINs.
  5. Ejecutar consultas analiticas con SQL avanzado (CTEs, Window Functions).
  6. Demostrar procesamiento de bajo nivel con RDD (map, filter, reduce).
  7. Generar KPIs de negocio y exportar en multiples formatos.
  8. Crear productor de eventos simulados en tiempo real con Kafka.
  9. Implementar consumidor con procesamiento en micro-batches.
  10. Desarrollar deteccion de anomalias y generacion de alertas.
  11. Almacenar datos con garantias ACID en MongoDB.
  12. Versionar codigo con flujo profesional en GitHub.

2. ARQUITECTURA BIG DATA Y FLUJO DEL DATO

Integrante 2 - Tiempo: 3 minutos

2.1 Arquitectura General del Sistema

Nuestra arquitectura sigue el modelo Lambda, un patron de diseno Big Data que combina procesamiento batch para analisis historico con procesamiento streaming para datos en tiempo real. La arquitectura se compone de tres capas principales:

Capa de Ingesta: Aqui es donde entran los datos. Usamos HDFS de Hadoop para guardar archivos grandes de forma distribuida y tolerante a fallos, y Kafka para recibir eventos en tiempo real. HDFS divide los archivos en bloques de 128MB replicados en multiples nodos.

Capa de Procesamiento: Utilizamos Apache Spark como motor central. Spark puede procesar archivos guardados (batch) mediante DataFrames, RDD y SQL, y tambien eventos en tiempo real (streaming) mediante Structured Streaming. Spark es hasta 100 veces mas rapido que MapReduce porque procesa datos en memoria RAM.

Capa de Almacenamiento: Los resultados se guardan en MongoDB, una base de datos NoSQL con propiedades ACID. Tambien exportamos a diferentes formatos como Parquet (columnar, comprimido) y JSON (para APIs).

2.2 Infraestructura con Docker Compose

Toda la infraestructura corre en contenedores Docker, lo que permite levantar un cluster Big Data completo con un solo comando y garantizar consistencia entre ambientes. Desplegamos 11 contenedores organizados en 4 clusters:

Cluster Contenedor Puerto Funcion

mongo-express 8082 Interfaz web

2.3 Flujo del Dato

Flujo Batch (Seccion D del AA4): Los archivos CSV, JSON y TXT se cargan en HDFS o se leen directamente. Spark DataFrames lee los archivos detectando automaticamente el esquema. Se eliminan registros con valores nulos, duplicados y outliers. Se renombran columnas, convierten tipos y crean columnas calculadas. Se unen las diferentes fuentes mediante JOINs. Se ejecutan consultas SQL y operaciones RDD. Finalmente se exportan resultados a CSV, JSON, Parquet y MongoDB.

Flujo Streaming (Seccion E del AA4): El productor Kafka genera eventos simulados de usuario (PLAY, PAUSE, RATE, SEARCH, ERROR). Los eventos se publican en topics de Kafka. Spark Structured Streaming consume los mensajes y los procesa en micro-batches cada 10 segundos. Se calculan metricas en ventanas temporales de 30 segundos y 1 minuto. Se detectan anomalias como actividad excesiva o errores frecuentes. Se generan alertas y los resultados se envian a consola, archivos JSON y MongoDB.

3. PROCESAMIENTO BATCH CON SPARK

Integrante 3 - Tiempo: 4 minutos

Seccion D de la Rubrica AA4 (4 puntos)

3.1 Por que Apache Spark

Apache Spark es el motor de procesamiento de datos mas utilizado en Big Data porque es hasta 100 veces mas rapido que tecnologias anteriores como Hadoop MapReduce. La velocidad de Spark se debe a que procesa los datos en memoria RAM en lugar de escribir constantemente al disco. Ademas, optimiza automaticamente los planes de ejecucion mediante el Catalyst Optimizer.

Spark ofrece tres abstracciones principales para trabajar con datos:

  • RDD (Resilient Distributed Dataset): Nivel mas bajo, control total sobre el procesamiento.
  • DataFrames: Datos estructurados con esquema, optimizacion automatica.
  • Spark SQL: Consultas SQL estandar sobre DataFrames.

3.2 RDD - Resilient Distributed Datasets

RDD es la abstraccion fundamental de Spark. Es una coleccion distribuida de objetos que se puede procesar en paralelo en multiples nodos del cluster. Las caracteristicas principales son:

  • Resiliente: Si un nodo falla, los datos se pueden reconstruir desde el origen.
  • Distribuido: Los datos se dividen en particiones procesadas en paralelo.
  • Inmutable: Una vez creado, no se modifica. Las transformaciones crean nuevos RDDs.
  • Lazy Evaluation: Las transformaciones no se ejecutan hasta que se solicita una accion.

Operaciones RDD implementadas en nuestro proyecto:

Tipo Operacion Descripcion Ejemplo
Transformacion map() Aplica funcion a cada elemento Extraer tipo de evento
Transformacion filter() Selecciona elementos Solo eventos ERROR
Transformacion reduceByKey() Agrupa y combina valores Contar por tipo
Accion collect() Trae resultados al driver Obtener conteo final
Accion count() Cuenta elementos Total de eventos

3.3 DataFrames - Datos Estructurados

DataFrames son como tablas de base de datos distribuidas en multiples servidores con optimizacion automatica de consultas.

Lectura de Archivos: Implementamos lectura de tres formatos diferentes: CSV (netflix_titles.csv), JSON (usuarios.json) y TXT (visualizaciones.txt). Spark infiere tipos automaticamente.

Limpieza de Datos: Aplicamos tres tipos de limpieza: eliminacion de nulos en campos criticos, eliminacion de duplicados basados en campos clave, y filtrado de outliers (registros con valores fuera de rangos validos).

Transformacion de Columnas: Renombramos columnas a espanol (title a titulo), convertimos tipos (release_year de string a integer), y creamos columnas calculadas como "decada" y "es_pelicula".

Integracion con JOINs: Unimos visualizaciones con usuarios por user_id, resultado con catalogo por show_id, y agregamos valoraciones.

3.4 Spark SQL

Spark SQL nos permite escribir consultas en lenguaje SQL estandar. Implementamos:

  • CTEs (Common Table Expressions): Subconsultas nombradas para organizar logica compleja.
  • Window Functions: ROW_NUMBER para rankings, SUM OVER para acumulados.
  • Agregaciones: COUNT, SUM, AVG, MAX, MIN agrupados por pais, genero o ano.

3.5 KPIs y Exportacion

KPIs de negocio calculados: total de titulos (8,807), distribucion por tipo (70% Movies, 30% TV Shows), rating promedio (3.8/5.0), pais mas productivo (United States con 2,818), genero mas popular (Dramas con 2,427).

Formatos de exportacion: CSV (reportes en Excel), JSON (APIs REST), Parquet (data warehouses).

4. MONGODB - MODELO DE DATOS ACID

Integrante 4 - Tiempo: 3 minutos

Modelo de Datos ACID de la Rubrica AA4 (4 puntos)

4.1 Por que MongoDB

Elegimos MongoDB porque es una base de datos NoSQL orientada a documentos que se adapta perfectamente a escenarios de Big Data donde la flexibilidad y escalabilidad son criticas.

Caracteristica SQL Tradicional MongoDB
Esquema Fijo, requiere migraciones Flexible, documentos JSON
Escalabilidad Vertical Horizontal (sharding)
Datos complejos Multiples tablas + JOINs Documentos anidados
Ideal para Transacciones complejas Big Data, tiempo real

4.2 Propiedades ACID

Aunque MongoDB es NoSQL, desde la version 4.0 soporta transacciones ACID multi-documento:

Propiedad Significado Implementacion
Atomicidad Transaccion completa o nada Transacciones multi-documento con session
Consistencia Datos cumplen reglas definidas Validadores de esquema en colecciones
Aislamiento Transacciones no se interfieren Read Concern y Write Concern
Durabilidad Datos persisten ante fallos Write Concern "majority" + journaling

4.3 Modelo de Colecciones

Nuestra base de datos netflix_analytics contiene 5 colecciones principales:

Coleccion Proposito Campos Principales Registros
catalogo Peliculas y series show_id, titulo, tipo, director, pais, ano, generos, duracion ~8,800
usuarios Perfiles de usuarios user_id, nombre, email, pais, plan, fecha_registro ~1,000
visualizaciones Historial de reproducciones user_id, show_id, fecha, duracion_minutos, dispositivo ~50,000
valoraciones Ratings de usuarios user_id, show_id, rating (1-5), fecha ~10,000
eventos_streaming Eventos en tiempo real event_id, user_id, tipo, timestamp, metadata Creciente

4.4 Carga de Datos desde Spark

Utilizamos el conector oficial MongoDB-Spark para escribir DataFrames procesados directamente a las colecciones. El proceso incluye: configuracion de URI de conexion, seleccion del DataFrame limpio y transformado, especificacion de la coleccion destino, definicion del modo (overwrite o append), y ejecucion paralela en multiples particiones.

4.5 Consultas de Agregacion

MongoDB ofrece un potente framework de agregacion. Consultas implementadas:

  • Distribucion por tipo: $group por tipo, $count
  • Top paises: $group por pais, $sort, $limit
  • Rating por genero: $lookup, $unwind, $group, $avg
  • Usuarios activos: $group por user_id, $sort, $limit
  • Errores recientes: $match timestamp mayor que (now - 5min) AND tipo = ERROR

Indices para optimizacion: catalogo.show_id (unico), catalogo.generos (multikey), usuarios.email (unico), visualizaciones.user_id, eventos_streaming.timestamp (descendente).

5.1 Apache Kafka - Streaming en Tiempo Real

Apache Kafka es un sistema de mensajeria distribuido disenado para manejar flujos de datos en tiempo real con alto rendimiento, tolerancia a fallos y escalabilidad.

Productor de Eventos (06_kafka_producer.py): Genera eventos simulados que representan acciones de usuarios:

  • PLAY (40%): Usuario inicia reproduccion
  • PAUSE (25%): Usuario pausa el video
  • RATE (15%): Usuario califica contenido (1-5)
  • SEARCH (15%): Usuario busca contenido
  • ERROR (5%): Error tecnico

Cada evento incluye: ID unico, usuario, tipo, contenido, timestamp, pais, dispositivo y metadatos.

Consumidor Spark Streaming (07_spark_streaming.py): Implementamos 5 streams de procesamiento:

Stream Ventana Funcion
Metricas por ventana 30 segundos Cuenta eventos por tipo
Usuarios activos 1 minuto Usuarios unicos por pais
Deteccion anomalias 1 minuto Alerta si usuario mayor que 50 eventos/min
Alertas de error Inmediato Notifica errores con severidad
KPIs tiempo real 20 segundos Plays totales, rating promedio

Contamos con tres interfaces web para monitorear el sistema:

  • Kafka UI (puerto 8083): Ver topics, inspeccionar mensajes en tiempo real, monitorear consumer groups.

  • Mongo Express (puerto 8082): Explorar colecciones, ejecutar consultas, ver datos insertados.

Estructura del Repositorio:

  • spark-apps/: Scripts Python (01 al 07)
